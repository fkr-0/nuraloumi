# Integrate NuraBrowser into the normal, complete NuraLoumi release bundle

## Goal
Make NuraBrowser a first-class, mandatory component of the **ordinary** official NuraLoumi SL101 release artifacts. An artifact advertised as containing NuraBrowser must contain a launchable native engine, WPEWebProcess, its required sandbox helpers and the complete hash-verified target ABI runtime, not merely `bin/nuraloumi-browser` or an optional, independently downloaded smoke-test tar. Implement the producer→package→verify chain and make incomplete output fail closed.

## Evidence and baseline
- Repository: NuraLoumi checkout; start from the current clean main revision, re-check HEAD and any existing release CI run before changing files.
- `.github/workflows/sl101-musl-armv7.yml` currently packages `nuraloumi-ci.tar` through `cargo xtask package` and signs a development Alpine .apk; it contains the Rust `nuraloumi-browser` launcher but no native engine.
- `.github/workflows/nurabrowser-engine-armhf.yml` and `scripts/ci-build-nurabrowser-engine.sh` independently produce `libexec/nuraloumi/browser/nurabrowser-core`, but currently from Debian ARMHF/glibc and with `web_process_sandbox=unqualified`, `dependency_instruction_closure=unqualified`, `device_deployment=forbidden`. **Never copy this glibc artifact into a musl release** or relabel it as qualified.
- Native browser sources live in `components/nura-browser-engine/`. Packaging logic: `crates/nuraloumi-xtask/src/package.rs`; release checks and target packages: `scripts/verify-ci-artifact.py`, `scripts/build-ci-alpine-apk.sh`, `scripts/test_verify_ci_artifact.py`, `scripts/test_native_packages_ci.py` and target workflows. Read the actual current files before selecting changes.
- Read `AGENTS.md`, `ROADMAP.md`, `DESIGN.md`, `docs/ARCHITECTURE.md`, `docs/CONTRACTS.md`, `docs/AGENT-LANES.md`, `docs/qualification/SL101-106-FUNCTIONAL-RELEASE-20261121.md`, and `docs/qualification/NURA-BROWSER-R3-WEBPROCESS-ISA-CLOSURE.md`. Do not duplicate the existing browser contract/test task `NURALOUMI-FIX-CLOSURE-20261121-03`; this task owns **the regular bundle and its CI integration**.

## Implementation scope
1. Trace how the standard musl ARMv7 artifact and, where compatible, Debian armhf artifact are created. Design one explicit target-specific browser runtime contract: source SHA, pinned producer revision, complete file tree, SHA256, ELF interpreter/DT_NEEDED/dlopen closure, VFPv3-D16/no-NEON/no-hardware-division checks and WPE WebProcess/sandbox process dependencies.
2. Wire the native engine/runtime into the **normal** `cargo xtask package`, CI `nuraloumi-ci.tar` and installable native package flow as a required product component. Use a reproducible same-revision producer stage or a strictly source-pinned, hash-verified artifact input; do not rely on host-local private binaries or an extra manual copy after installation. Preserve the software/Pixman fallback and the independent GPU-video opt-in path.
3. Implement an actual musl-compatible WPE runtime producer or an explicitly isolated, fully verified glibc runtime design **if technically defensible**. The existing Debian glibc smoke builder is not sufficient. If a qualified runtime cannot yet be produced, still implement meaningful package/manifest/verifier/CI negative contracts that prevent falsely successful browser-inclusive releases; state a specific actionable remaining producer gap without inventing PASS.
4. Ensure stable `libexec/nuraloumi/browser/` resolution through versioned releases, correct loader/library search isolation, WebProcess and sandbox helper discovery, and desktop/browser launcher contract. Do not disable WebKit sandbox, use `WEBKIT_USE_SANDBOX=0`, remove ISA gates, or contaminate the player/GStreamer runtime.
5. Add positive and negative tests for absent engine, missing WPEWebProcess/helper/module, altered digest, wrong source SHA, glibc↔musl mismatch, forbidden ARM instruction, stale version and partial archive. Verify normal tar + APK or Debian package contents as applicable; do not treat host tests as physical SL101 success.

## Guardrails and integration
- Work in an isolated worktree or with exclusive workspace path claims after inspecting live workers, claims and current changes. Preserve all unrelated source and untracked data; coordinate overlapping CI/packaging lanes rather than overwriting their work.
- This is a host/code+CI task, **not a tablet deploy**. Do not alter running Sway, device files, firmware, bootloader, kernel, Mesa system installation or recovery. No default activation or device SSH. Push/remote CI only if authorized under current repo policy and independently verified; otherwise leave a reviewed commit ready for normal owner release integration.
- The owner has established the target tablet's identity and recovery path; do not introduce unrelated permission-ceremony blockers.
- Run at least focused `python3 -m unittest scripts/test_browser_engine_ci.py scripts/test_verify_ci_artifact.py scripts/test_native_packages_ci.py -v`, browser engine tests (`python3 -m unittest discover -s components/nura-browser-engine/tests -p 'test_*.py' -v`), relevant Rust/xtask tests, workflow syntax lint where available, and broader `cargo test --locked --workspace` / Clippy when practical. Record exact command, exit and any skipped tests. Use an offline package fixture to prove both a complete accept case and an incomplete reject case.
- Commit coherent scoped source/test/docs changes on a named branch, or provide an exact reviewed patch and finite implementation blocker if a package source cannot be qualified. Do not claim deployed or fully working browser from CI alone.
