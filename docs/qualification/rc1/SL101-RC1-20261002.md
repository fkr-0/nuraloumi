## 100x persistent menu open/close soak

This was a real menu lifecycle test, **not** 100 process restarts.

A single `nuraloumi-panel --live` process stayed running. A temporary
`/dev/uinput` virtual direct-touch device tapped the deterministic Search
center at logical `x=624,y=20`; a temporary virtual keyboard sent two Escape
presses per cycle:

- first Escape clears launcher search focus/query state;
- second Escape closes the transient launcher surface.

The same persistent panel PID and the same labwc PID survived all 100 cycles.

## Startup/readiness latency

layer-shell configure and first wl_buffer attach:

```text

3       765.717          864.926
4       713.686          822.972
5       676.222          774.790
```

Observed first-attach range: **774.790–864.926 ms**.

This is a reproducible diagnostic measurement but not an authoritative
first-visible-frame result because `WAYLAND_DEBUG` materially perturbs the
startup path. A second attempt to time the visible frame by polling the top
40 rows of `/dev/fb0` did not observe compositor changes, so fbdev cannot be
used as a scanout clock on this setup.

Status: **PENDING / performance concern**. The <=250 ms first-interactive-frame
target is not yet demonstrated.

## Suspend / resume

Status: **PENDING physical**.

No remote suspend was issued because there is no independently qualified
automatic wake path. Deliberately suspending a remote-only recovery device
without proven RTC wake would turn a release test into a potential availability
failure. Final RC1 should perform suspend with a human present to resume the
tablet, then verify:

1. panel surface recovery;
2. touch;
3. slider keyboard;
4. provider refresh;
5. menu open/close;
6. labwc continuity or clean compositor restart evidence.
