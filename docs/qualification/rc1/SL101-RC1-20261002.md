## Startup/readiness latency

The initial RC evidence identified the real blocker rather than a rendering
cost: live startup executed `ProbeSnapshot::live()` before connecting to
Wayland. Five direct probe runs took 634.81–651.76 ms (median 646.78 ms), and
the eight serial external-provider commands measured about 779 ms in aggregate
on the tablet.

Commit `6987a87` moves that initial probe off the critical path. Live mode now
creates/presents the panel from the safe default snapshot, runs the one-shot
provider probe concurrently, keeps servicing Wayland while it is pending, and
refreshes panel plus any open menu once the result arrives.

The exact qualified ARMv7 panel binary had SHA-256
`c6dab9950d67030acc5287340a33574f88432de0107cf51bcbbdd1f6f0a90ade`.
Using raw nonblocking reads of `WAYLAND_DEBUG` output avoids the buffered-I/O
measurement artifact seen in the earlier diagnostic. Five real SL101 launches
measured:

```text
run   first attach ms   Search touch injected   menu layer request ms   provider ready ms
1         212.19              220 ms                    332.45              1009.84
2         189.09              220 ms                    335.01               902.89
3         178.50              220 ms                    331.20               993.77
4         175.82              220 ms                    342.41              1050.54
5         193.22              220 ms                    369.74               867.52
```

First-attach median: **189.09 ms**; range: **175.82–212.19 ms**.
All five first panel buffer attaches are below the 250 ms budget.

The Search touch was intentionally injected while providers were still loading.
Every run produced the transient menu request before provider readiness, proving
the event loop is responsive during the deferred probe rather than merely
painting an early frozen frame. labwc remained PID 20187 before/after.

Status: **PASS at the live client/compositor interaction boundary** for the
<=250 ms first responsive panel-frame budget. No claim is made that this is a
photodiode/scanout timestamp; `/dev/fb0` is not a usable compositor scanout
clock on this device.

## Suspend / resume

Status: **PENDING physical**.

No remote suspend was issued because there is no independently qualified
automatic wake path. Deliberately suspending a remote-only recovery device
without proven RTC wake would turn a release test into a potential availability
failure. Final RC1 should perform suspend with a human present to resume the
tablet, then verify:

1. panel surface recovery;
2. touch;
3. slider keyboard;
4. provider refresh;
5. menu open/close;
6. labwc continuity or clean compositor restart evidence.
